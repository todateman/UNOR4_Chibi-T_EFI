# 10Hzロギング機能 実機動作検証レポート

**日付**: 2026-09-12
**対象**: `feature/10HzLogging` ブランチ (Arduino UNO R4 Minima ベース ECU)
**対象コミット**: `a17eb59` (HEAD, 2026-08-30) / 検証対象は以下3コミット

- `b2dbaca` 10Hzでロギングするための高速化・負荷低減
- `3b4a6ba` ロギングフォーマットを改善し、小数出力データの欠損を整数演算で修正
- `a17eb59` 安全のため、キルスイッチOFFでスタータを強制停止

**目的**: Serial1の10Hzロギングが周期・フォーマットとも問題なく動作しているか、およびキルスイッチによるスタータ強制停止が安全に機能しているかの確認

## 1. デバッグ環境

| 機器 | 詳細 |
| ---- | ---- |
| ECU | Arduino UNO R4 Minima (RA4M1)、`feature/10HzLogging` 書き込み済み |

| オシロスコープ | RIGOL DHO804 (`USB0::6833::1101::DHO8A253701207::0::INSTR`) |

### オシロスコープ チャンネル割り当て（`debug_report_20260330.md`と同一）

| CH | ピン | 信号 | 説明 |
| -- | ---- | ---- | ---- |
| CH1 | D9 | NE_Z_IN | クランク角0°基準パルス (1/rev) — RPMクロスチェックに使用 |
| CH2 | D2 | NE_A_IN | クランク角エンコーダAパルス (360/rev) |
| CH3 | A0 | INJ_OUT | 燃料噴射出力 (Active-LOW) |
| CH4 | A1 | IGN_OUT | 点火出力 (Active-LOW) |

今回はプローブの付け替えは行わず、STR_OUT(A2)の挙動はSerial1ログ・CH3/CH4のパルス有無・実機の目視/オシロ画面によるユーザー確認で代替した。

### 補足: visa-mcp 接続時の注意点

`send_visa_command` を `protocol="usb"` で呼ぶ際、`resource_id` は `list_visa_resources` が返す文字列をそのまま渡す（例: `USB0::6833::1101::DHO8A253701207::0::INSTR`）のではなく、**先頭の `USB0::` と末尾の `::INSTR` を除いた中間部分のみ**（例: `6833::1101::DHO8A253701207::0`）を渡す必要がある。  
誤った形式で呼ぶと `'read_termination' is not a valid attribute for type Resource` という一見無関係なエラーになる（サーバー側が組み立てるVISAアドレスが二重になり、pyvisaがUSB INSTRとして正しく解決できずメッセージベースでない`Resource`型にフォールバックするため）。

## 2. 検証結果

### 2-1. Serial1 10Hz周期・フォーマット検証（アイドル、60秒間連続取得）

| 項目 | 結果 |
| ---- | ---- |
| 取得パケット数 | 601 |
| パケット間隔 平均 | **100.000 ms** |
| パケット間隔 標準偏差 | 0.117 ms |
| パケット間隔 範囲 | 99.623 〜 100.392 ms |
| 60秒間の累積ドリフト | 0.2 ms（0.000%） |
| フォーマット欠損（小数部・フィールド数） | **0 件 / 601行** |
| RPM安定性（アイドル） | 894〜895（安定） |

`b2dbaca`（10Hz化）・`3b4a6ba`（小数欠損修正）とも、長時間動作でも周期ドリフトやフォーマット崩れは確認されなかった。

### 2-2. RPM精度クロスチェック（オシロCH1周波数 vs Serial1ログ、低・中・高回転）

| 回転域 | オシロ実測(CH1) | 換算RPM | Serial1ログRPM | 周期 平均/標準偏差 |
| ------ | ---------------- | ------- | -------------- | ------------------ |
| 低速(アイドル) | 14.911〜14.915 Hz | 894.7〜894.9 | 894〜895 | 100.000 / 0.117 ms |
| 中速 | 65.705 Hz | 3942.3 | 3940〜3944 | 100.006 / 0.282 ms |
| 高速 | 99.753 Hz | 5985.2 | 5981〜5988 | 100.001 / 0.208 ms |

いずれもオシロ実測RPMとログRPMがほぼ一致（誤差0.1%未満）。整数演算化によるRPM計算・ロギングへの悪影響なし。

> 高速域の取得開始直後の1行のみ `RPM=42` を含む破損行（フィールド数不整合）が観測された。　　
> これは新規にシリアルポートをオープンした直後の最初の1行のみで発生し、以降は即座に正常なCSV行に復帰していた。　　
> 同一の事象は他3回のキャプチャ開始時には発生しておらず、ポートオープン時にOS側バッファの途中から読み取りを開始したことによる**計測ツール側の既知の現象**と判断し、ファームウェア側の問題ではないと結論づけた。

### 2-3. キルスイッチOFF→スタータ強制停止（`a17eb59`）

以下2パターンで実機・オシロ双方で確認した。

**パターンA: スタートスイッチON保持 → キルスイッチOFF（エンジン停止） → スタートスイッチを離す → キルスイッチON（エンジン運転可能）**  

- キルスイッチOFFの瞬間、`updateEngineMap()`の切替（`startState==LOW`時のみ始動マップ値 INJ=8.0ms/IGN_CA=0°を使用）とあわせてSerial1ログ上でも状態遷移を確認。
- ユーザーがSerial1シリアル出力とオシロ波形（CH3/CH4のINJ/IGNパルス停止）を目視確認し、問題なし。

**パターンB: スタートスイッチON保持のまま一切離さずキルスイッチOFF→ON**  

- キルスイッチOFFでSTR_OUTが即座にOFFになることをオシロで確認。
- スタートスイッチには一切触れていないにもかかわらず、キルスイッチをONに戻した瞬間にSTR_OUTが**自動的に再度ON**になることをオシロで確認。

| 評価項目 | 結果 |
| -------- | ---- |
| キルスイッチOFFでスタータ即時強制停止 | **合格**（2パターンとも確認、再現性あり） |
| キルスイッチOFF→ON時、スタートスイッチ保持中は自動的にスタータ再投入 | 確認済み（**仕様通り**の挙動） |

コード上（`src/main.cpp:428-445`）、`ENGOFF_IN`（キルスイッチ）がOFFの分岐では `startState` の値に関わらず無条件で `STR_OUT=HIGH` に強制し、ONの分岐では毎サイクル `startState==LOW` をレベル判定してスタータを投入する実装になっている。  
そのため「キルスイッチOFFで確実にスタータが止まる」ことは保証されるが、「スタートスイッチを押し直さない限りキルスイッチON後もスタータが再投入されない」という設計にはなっていない（エッジ検出ではなくレベル判定のため）。  
今回の実機確認では、この挙動はユーザーの想定通りであることが確認された。

## 3. 結論

| 評価項目 | 結果 |
| -------- | ---- |
| Serial1が10Hz（100ms周期）で安定出力されているか | **合格**（stdev 0.117〜0.282ms、ドリフト0.000%） |
| CSVフォーマットの小数欠損有無（`3b4a6ba`） | **合格**（欠損0件） |
| RPM値の妥当性（低・中・高回転、整数演算化の影響） | **合格**（オシロ実測との誤差0.1%未満） |
| キルスイッチOFFでのスタータ強制停止（`a17eb59`） | **合格**（2パターン・再現性確認済み） |

**`feature/10HzLogging` ブランチの3コミット（10Hz化・フォーマット修正・キルスイッチ安全停止）はいずれも実機・実信号上で意図通り動作していることを確認した。**
